# Provenance Specification

**Version:** 1.0.0
**Status:** CANONICAL

## 1. Objective
To guarantee that every prediction generated by the OS can be mathematically and logically traced back through its entire dependency chain, down to the original astronomical data source. Without this, ensemble convergence is statistically meaningless.

## 2. The Provenance Chain
Provenance must reconstruct the entire knowledge graph of a prediction:

`Final Statement (LLM)`
↓
`Prediction (Normalized Node)`
↓
`MethodRun (Methodology Context)`
↓
`Rule / Hypothesis (Astrological Logic)`
↓
`Calculation Object (e.g. Shadbala Result)`
↓
`AstroState (Canonical Snapshot)`
↓
`ConventionProfile (Parameters)`
↓
`AstronomyEngine (Code Version)`
↓
`BirthInput (Raw Source Data)`

## 3. Structural Requirements

Every `Prediction` must explicitly declare a `provenance` dictionary/object containing at minimum:
- `astro_state_id`: The immutable UUID of the `AstroState` consumed.
- `method_id`: The ID of the methodology that produced it.
- `method_version`: The strict version string.
- `rules_triggered`: An array of rule identifiers (e.g. `["parashari_dasha_rule_5", "sade_sati_moon"]`).
- `transit_datetime`: (If applicable) The exact UTC datetime of the transit chart used.

Every `AstroState` must explicitly declare `ComputationProvenance`:
- `engine_version`: The semantic version of the Python deterministic engine.
- `ephemeris_source`: The data source used (e.g., `swiss_ephemeris`).
- `ephemeris_version`: The underlying version of the ephemeris binary/data.
- `timestamp_utc`: When the calculation was performed.
- `convention_id`: The ID of the `ConventionProfile` used.

## 4. Implementation Rules
- A plain text field called `"provenance": "Calculated by system"` is STRICTLY FORBIDDEN.
- If provenance cannot be completely reconstructed, the prediction MUST NOT be persisted or evaluated.
- Provenance should eventually support hash-based integrity (e.g., SHA-256 of the `AstroState`) to ensure the source data was not tampered with post-calculation.
